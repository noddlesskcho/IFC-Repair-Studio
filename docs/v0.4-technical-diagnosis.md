# IFC Repair Studio v0.4 technical diagnosis

## Root causes found in v0.3

The source IFC was opened with `ifcopenshell.open()` after a streaming STEP-envelope
check. Scan and repair were separate user actions, so repair reopened the source once;
within one repair operation the source was not parsed twice.

The slab scope was collected through `IfcSlab.Representation` and the directly owned
`IfcProductDefinitionShape.Representations`. The semantic index built project-rooted
contexts and ownership maps once. Context resolution was nevertheless repeated for
every affected representation even when thousands shared the same product/identifier/
representation/item signature.

The targeted writer created a temporary file in the output directory, scanned the
source with a native regular expression, copied unchanged mmap ranges, replaced only
the selected `ContextOfItems` token, flushed, and called `fsync`. It wrote one output
stream and did not copy the temporary output afterward. `os.replace()` installed the
temporary file on the same volume.

The status text `Writing atomic output` was misleading because it covered much more
than the write. After writing, v0.3 reopened the complete temporary IFC, ran full
IfcOpenShell/EXPRESS validation, ran targeted validation, iterated representation items,
built another whole-model snapshot, calculated a SHA-256 checksum, compared snapshots,
and only then performed `os.replace()`. No intermediate worker progress was emitted, so
the last visible status remained `Writing atomic output`. The GUI event loop itself was
not blocked by scan/repair because they ran in `QThread`, but PDF/JSON/CSV generation
was invoked by the GUI completion slot and could block the GUI for a large report.

The temporary file was already on the destination volume. A filesystem `copy2()` was
used only for backup mode. v0.3 default UI selected replace-original mode, renamed the
source to `_backup`, and could produce confusing repeated suffixes. Worker exceptions
were caught, but only the exception type and message reached the UI; stage, traceback,
temporary path, and log path were not preserved. Cancellation was checked between
native stages and could not interrupt IfcOpenShell parsing or validation. Whole-model
snapshots and validation logs could substantially increase memory use.

## v0.4 processing path

1. Read input metadata and validate the STEP envelope.
2. Open and parse the source once for the current operation.
3. Collect direct IfcSlab representations once.
4. Build the context index once.
5. Resolve each unique rule signature once and reuse the result.
6. Build explicit `RepairTarget` records under `SLAB_MISSING_SHAPE_CONTEXT_V1`.
7. Write one temporary output in the destination folder.
8. Check the temporary size and IFC header/footer.
9. Verify every intended repair using the writer's exact output-offset manifest.
10. Optionally reopen and run full IFC validation only when selected.
11. Atomically install the verified output with `os.replace()`.
12. Generate PDF/JSON/CSV and diagnostic logs in the worker thread.
13. Clean up temporary output on failure or cancellation.

Save As is now the default and never changes the source. Overwrite mode first creates a
deterministically named `.original.ifc` backup and requires a dedicated review dialog.

## Measured performance

The supplied 652,895,459-byte sample produced the verified counts:

- elements scanned: 2,552;
- affected elements: 2,051;
- representations scanned: 4,851;
- affected representations: 3,151;
- Body / SweptSolid: 1,100;
- FootPrint / Curve2D: 2,051.

A warm v0.4 scan took 27.501 seconds: native IFC opening 23.096 seconds, slab target
collection 0.027 seconds, context indexing 0.053 seconds, and context resolution 0.084
seconds. The first complete fast repair took 49.443 seconds: native opening 23.581,
temporary serialization 11.032, full-output regex verification 10.457, and atomic
replacement 0.001 seconds. Manifest verification subsequently measured 0.014 seconds
on the 300,000-record synthetic benchmark, eliminating the second complete output scan.

Cold filesystem cache, antivirus, storage speed, and native IfcOpenShell allocation can
change these timings. Full validation remains optional because it requires another
complete parse and may dominate runtime.

## Known limitations

- IfcOpenShell parsing and full schema validation do not expose safe mid-call
  cancellation or granular progress.
- The fast writer is STEP-targeted but its targets and context proposals come only from
  schema-aware rule detection. It never repairs a global regex match by itself.
- Fast verification proves the selected assignments and STEP envelope, not every IFC
  schema rule or downstream CORENET X compatibility.
- Save As needs free space for one additional model. Overwrite mode needs space for a
  backup and temporary output.
- The in-memory IfcOpenShell model is intentionally reopened between separate Scan and
  Repair user actions to avoid retaining hundreds of megabytes indefinitely and to
  avoid stale-file repairs.
